Magister Renderer Project Guide

A short explanation of what this OpenGL project currently does and how the main pieces fit together.

Goal of the project: build a small OpenGL renderer that can later compare forward rendering, deferred shading, and visibility buffer techniques in a controlled scene.

1. What the project currently is

The current codebase is a minimal OpenGL application. It opens a window, creates a camera, loads a shader, builds a small cube mesh, and draws that mesh every frame. This is the foundation that later rendering techniques will be added on top of.

2. Main program flow

  1. main.cpp starts GLFW and creates the OpenGL window.
  2. GLAD is loaded so OpenGL functions are available.
  3. A Camera object is created to handle the view and projection matrices.
  4. A SimpleScene object creates the cube geometry in GPU buffers.
  5. Each frame, the program handles input, updates the scene, clears the screen, and draws the cube(s).

3. File-by-file explanation

src/main.cpp

This is the application entry point. It creates the window, sets up callbacks for resizing and mouse movement, enables depth testing, and runs the main rendering loop. It also reads keyboard input for movement and exits when ESC is pressed.

src/rendering/Camera.cpp

The camera stores position, yaw, pitch, field of view, and aspect ratio. It produces:

  • a view matrix using glm::lookAt
  • a projection matrix using glm::perspective
  • keyboard movement with W, A, S, D
  • mouse look control for rotating the view
src/rendering/SimpleScene.cpp

This file creates the cube mesh and stores the vertex/index data in OpenGL buffers. In the render function, it builds a model matrix for each cube, combines it with the camera matrices, and sends the final matrix to the shader through the uMVP uniform.

shaders/fullscreen.vert

This vertex shader transforms cube vertices from model space into clip space. It also passes world position and normal data to the fragment shader so lighting calculations can be done later.

shaders/solid_color.frag

This fragment shader is very simple. It uses the current fragment depth to blend between two colors: a warm near color and a cooler far color. That creates a depth-based tint rather than real lighting. It is useful as a placeholder shader, but it is not yet the final lighting system.

4. What you should see on screen

When the program runs, you should see a cube rendered in the window with a background color. If the cube is rotated or moved, its faces may appear different because of perspective, but the geometry should still be a cube. If the scene looks broken, the likely causes are camera position, face culling, or the transform setup.

5. Controls

  • W, A, S, D: move the camera
  • Mouse movement: look around
  • ESC: close the window

6. Why the cube may look odd

The cube can look stretched, clipped, or strange when the camera gets too close, when the object is rotated, or when back faces are hidden by culling. That does not necessarily mean the geometry is wrong. It usually means the current scene is still only a basic test scene, not a polished demo scene.

7. What comes next

  1. Keep the forward-rendering baseline stable.
  2. Add real lighting using normals and one or more lights.
  3. Use the same scene for deferred shading later.
  4. Compare the two approaches on the same visual setup.
Important idea: this current code is a learning baseline. It is meant to help you understand the rendering pipeline before introducing the more complex deferred shading and visibility buffer work.
